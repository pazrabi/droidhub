# Phone Hub — план проекта

Одна программа («хаб») на сервере в Амстердаме, через которую:
- я управляю любым из своих Android-телефонов с любого устройства и из любого места (через браузер);
- Claude и мой Gemini pool получают доступ к телефонам как к инструментам (MCP);
- мои сервисы (в первую очередь Telegram-бот авиабилетов `aviaticket`) пользуются ресурсами телефонов: домашним IP и мобильным Chrome.

---

## 1. Исходные данные

| Что | Значение |
|---|---|
| Сервер | арендованный VPS в Амстердаме (ОС уточнить: скорее всего Ubuntu; **проверить первым делом**) |
| Домен | неизвестно, есть ли (**спросить**). Если нет, временно можно использовать `<ip>.sslip.io` + Let's Encrypt |
| Телефон 1 | Realme C21Y (слабый: Unisoc T610, Android 11) |
| Телефон 2 | Redmi Note 11 (Android 11–13, MIUI/HyperOS) |
| Сеть телефонов | только домашний Wi-Fi, SIM-карт нет. **Значит, у обоих телефонов один и тот же домашний IP** |
| Рабочий комп | MacBook |
| Уровень владельца | начинающий вайбкодер: объяснять шаги простыми словами |

## 2. Архитектура

```
 [MacBook / любой браузер]      [Claude, Gemini pool]       [aviaticket бот]
            │ HTTPS                    │ MCP (HTTPS)               │ HTTP API / прокси
            └──────────────┬───────────┴───────────────────────────┘
                           ▼
              ┌─────────────────────────────┐
              │   HUB (сервер, Амстердам)   │
              │  FastAPI: веб-панель, API,  │
              │  MCP-сервер, менеджер       │
              │  устройств, логи действий   │
              │  Caddy (HTTPS) перед ним    │
              └──────────────┬──────────────┘
                             │ Tailscale (приватная сеть)
                             │ ADB по TCP (порт 5555)
              ┌──────────────┴──────────────┐
              ▼                             ▼
      [Realme C21Y]                  [Redmi Note 11]
   дома, на зарядке, Wi-Fi        дома, на зарядке, Wi-Fi
```

Ключевые решения:
- **Связь сервер ↔ телефоны** идёт через **Tailscale**: у каждого телефона постоянный адрес `100.x.x.x`, наружу ничего не открываем.
- **Управление** на первом этапе через **ADB** (`adb connect 100.x.x.x:5555`), своё Android-приложение не пишем.
- **Стек**: Python 3.11+, FastAPI, официальный MCP Python SDK (streamable HTTP), Caddy для HTTPS, systemd для автозапуска. Фронт панели простой: HTML + немного JS, без тяжёлых фреймворков.
- Всё, что умеет хаб, реализовано **один раз** в слое `devices/` (Python-функции), а веб-панель, HTTP API и MCP только вызывают эти функции.

## 4. Этапы

Каждый этап должен давать что-то работающее. Не переходить к следующему, пока критерий готовности не выполнен и владелец не проверил его сам.

### Этап 0. Подготовка инфраструктуры (вместе с владельцем, руками)
1. Узнать ОС сервера, есть ли домен, как владелец туда заходит (ssh).
2. Установить Tailscale на сервер, MacBook и оба телефона, войти в один аккаунт.
3. На телефонах (написать инструкцию в `docs/phone-setup.md`):
   - включить режим разработчика, «Отладку по USB», «Не выключать экран при зарядке»;
   - Redmi: дополнительно «Отладка по USB (настройки безопасности)», иначе не работают тапы и ввод (нужен вход в Mi-аккаунт и SIM… если без SIM не включается, искать обходной путь и сообщить владельцу);
   - убрать блокировку экрана (или поставить без пароля);
   - отключить оптимизацию батареи для Tailscale, включить для него «Постоянный VPN»;
   - один раз по USB с MacBook: `adb tcpip 5555`;
   - если в телефоне есть ограничение заряда / оптимизированная зарядка, включить.
4. Проверка с сервера: `adb connect <tailscale-ip>:5555` и `adb devices` → оба телефона `device`.

**Готово, когда:** с сервера `adb -s <ip>:5555 shell input keyevent KEYCODE_HOME` нажимает «Домой» на каждом телефоне.

### Этап 1. Ядро: менеджер устройств и действия
- `adb.py`: асинхронный вызов adb с таймаутами, понятные ошибки («телефон оффлайн» и т.п.).
- `manager.py`: читает `devices.yaml`, каждые ~30 с проверяет связь, при обрыве делает `adb connect`; хранит статус: онлайн, заряд, температура батареи, экран вкл/выкл.
- `actions.py`:
  - `screenshot(device, max_width=720)` → PNG/JPEG (уменьшать, чтобы не гонять мегабайты);
  - `tap(x, y)`, `swipe(x1, y1, x2, y2, ms)`, `long_press`;
  - `type_text(text)`: **важно: `adb shell input text` не умеет кириллицу и эмодзи.** Ставим на телефоны ADBKeyBoard (или аналог) и вводим через broadcast; латиницу можно обычным `input text`;
  - `key(name)`: back, home, recents, enter, power, volume;
  - `open_app(package)`, `list_apps()`, `open_url(url)`;
  - `ui_dump()`: `uiautomator dump` → упрощённый список элементов (текст, id, кликабельность, координаты центра). Это главный инструмент для ИИ: дешевле и точнее скриншотов;
  - `wake_and_unlock()`;
  - `shell(cmd)`: только для владельца/с отдельным флагом, в MCP выключен по умолчанию.
- Журнал действий (`audit.py`) в SQLite.
- Мини-CLI для проверки: `python -m hub.cli screenshot realme`.

**Готово, когда:** с сервера из CLI можно сделать скриншот, тапнуть и ввести русский текст на обоих телефонах.

### Этап 2. Веб-панель + авторизация + HTTPS
- Логин/пароль (хэш в `.env`), сессия в cookie, ограничение попыток входа.
- Страница «Устройства»: карточки телефонов со статусом.
- Страница телефона: экран (MVP: автообновление скриншота 1–3 раза в секунду), клик по картинке = тап по телефону, свайп мышью, поле ввода текста, кнопки Назад/Домой/Недавние/Питание, список приложений.
- Должно нормально работать с телефона (айфона) в браузере: адаптивная вёрстка, тач-события.
- Caddy + HTTPS, хаб слушает только localhost, наружу торчит только Caddy.
- systemd-сервис, автозапуск после перезагрузки сервера.

**Готово, когда:** владелец с MacBook вне дома (например, через мобильный интернет) открывает `https://<домен>`, логинится и управляет обоими телефонами.

### Этап 3. MCP-сервер для Claude и Gemini pool
- Эндпоинт `/mcp` (streamable HTTP) на том же домене.
- Инструменты: `list_devices`, `device_status`, `screenshot`, `ui_dump`, `tap`, `tap_element` (по тексту/id из ui_dump), `swipe`, `type_text`, `press_key`, `open_app`, `list_apps`, `open_url`, `wait`. Каждый принимает `device_id`.
- Хорошие описания инструментов: модель должна понимать, что сначала надо вызвать `ui_dump`/`screenshot`, а потом действовать.
- Авторизация по токену. Проверить, какие способы авторизации поддерживают коннекторы claude.ai (bearer-заголовок, OAuth или секрет в URL), и сделать совместимый вариант; секретный путь `/mcp/<длинный-токен>` оставить запасным вариантом.
- Лимиты: не больше N действий в минуту на устройство, всё пишется в журнал.
- Инструкция в README: как подключить хаб в Claude (claude.ai коннектор и Claude Code) и в Gemini pool.

**Готово, когда:** в чате с Claude можно попросить «открой на realme Chrome и найди погоду в Самаре», и это получается.

### Этап 4. Ресурсы телефонов для бота
Честное ограничение: без SIM-карт оба телефона выходят в интернет с **одного домашнего IP**. Это всё равно лучше серверного IP (домашние IP банят реже), но «два разных IP» не получится, пока нет SIM.

4a. **Прокси через телефон**
- На телефоне запускаем прокси (вариант: Termux + `microsocks`/`tinyproxy` с автозапуском через Termux:Boot; выбрать самое надёжное и описать в `docs/phone-setup.md`).
- Прокси доступен только внутри Tailscale (`100.x.x.x:1080`), снаружи его нет.
- Хаб показывает статус прокси и даёт боту адрес прокси через API: `GET /api/proxies`.

4b. **Мобильный Chrome как браузер для парсинга**
- `adb forward tcp:<порт> localabstract:chrome_devtools_remote` → Playwright `connect_over_cdp` к Chrome на телефоне.
- API хаба: `POST /api/devices/{id}/browser/fetch {url, wait_for?, js?}` → HTML/текст/скриншот страницы. Очередь: один запрос на телефон за раз.
- Сначала проверить на прототипе, что это стабильно работает на обоих телефонах (особенно Realme: он слабый).

Интеграция с `aviaticket`: в боте добавить режим «ходить через хаб» (прокси или fetch через телефон) с откатом на текущий Chromium, если хаб недоступен. Сам код бота трогать только с согласия владельца.

**Готово, когда:** бот получает выдачу хотя бы одного агрегатора через телефон.

### Этап 5. Надёжность
- Проблема: после перезагрузки телефона `adb tcpip 5555` слетает. Варианты по возрастанию сложности:
  1. панель показывает «телефон перезагрузился, подключи по USB и выполни команду» + уведомление в Telegram;
  2. беспроводная отладка Android 11+ (pairing) с автоматизацией;
  3. своё маленькое Android-приложение-агент (этап 6).
- Уведомления в Telegram: телефон оффлайн, перегрев, заряд падает (значит, отошла зарядка).
- Бэкап `config/` и базы журнала.

### Этап 6 (позже, по желанию). Своё Android-приложение-агент
Само держит соединение с хабом (WebSocket через Tailscale), управляет через AccessibilityService, делает скриншоты через MediaProjection, стартует при загрузке. Убирает зависимость от ADB. Плюс живое видео экрана (или интеграция scrcpy / ws-scrcpy в панель вместо скриншотов).

### Этап 7 (позже). Агент на Gemini pool
Цикл «ui_dump/скриншот → Gemini → действие» для задач, которые надо выполнять без меня, если сам пул не умеет вызывать MCP-инструменты.

## 5. Безопасность (обязательно с первого этапа)
- Хаб даёт полный доступ к телефонам, поэтому никаких открытых портов, кроме 443 (Caddy) и ssh.
- ADB и прокси доступны **только** через Tailscale.
- Пароль панели и токены MCP/API живут в `.env`, `.env` не попадает в git.
- Журнал всех действий; в MCP по умолчанию выключен произвольный `shell`.
- На этих телефонах не логиниться в банки и важные аккаунты.
