# Памятка оператора: 8-часовой USB-пилот DroidHub Desktop (Soak-тест)

Данный регламент предназначен для оператора стенда при проведении 8-часового стресс- и ресурсного тестирования (soak-тест) стабильности USB-подключений и приложения DroidHub Desktop.

> [!IMPORTANT]
> **Разграничение метрик**: Не путайте порог **p95** с длительным прогоном (soak-тестом).
> - Порог **p95** замеряется в отдельной изолированной серии тестов производительности и латентности.
> - Длительный прогон (soak-тест) оценивает долговременную стабильность: отсутствие утечек ресурсов (RSS), корректность циклов переподключения USB, нулевой уровень сбоев и корректность завершения процессов.

---

## 1. Локальные shell-переменные стенда

Перед началом работы инициализируйте переменные сессии. Задавайте пути и псевдонимы устройств в виде шаблонов без персональных абсолютных путей и реальных серийных номеров:

```bash
# Пути к приложению и рабочему пространству
APP_PATH="/Users/.../.app/Contents/MacOS/DroidHub"
WORKSPACE_PATH="/path/to/workspace"

# Серийные номера тестовых устройств (шаблоны)
SERIAL_1="SERIAL_DEVICE_1"
SERIAL_2="SERIAL_DEVICE_2"

# Выбранное целевое устройство для 20 циклов переподключения USB
TRACK_SERIAL="${SERIAL_1}"

# Файлы результатов (только новые пути, без перезаписи)
PILOT_DB="output/pilot_soak_$(date +%Y%m%d_%H%M%S).db"
PILOT_EVENTS="output/pilot_events_$(date +%Y%m%d_%H%M%S).jsonl"
SNAPSHOT_DB="output/pilot_snapshot_$(date +%Y%m%d_%H%M%S).db"
INTERRUPT_EVENTS="output/pilot_events_interrupted_$(date +%Y%m%d_%H%M%S).jsonl"

# PID для внешней проверки состояния (если DroidHub уже запущен)
DESKTOP_PID="12345"
```

---

## 2. Правило одного инстанса Desktop и завершение работы

- **Строго один инстанс Desktop**: В операционной системе должен быть запущен ровно один экземпляр DroidHub Desktop.
- **Штатное закрытие старого процесса**: Если старый процесс уже запущен, оператор дожидается завершения активных задач и закрывает его штатно (через UI / Cmd+Q). Применение деструктивных команд принудительного завершения (например, `kill -9`) запрещено.
- **Управляемый запуск vs `--desktop-pid`**:
  - Для основного прогона используется управляемый запуск через параметр `--desktop-command "${APP_PATH}"`. Только в этом режиме регистратор контролирует жизненный цикл приложения и валидирует реальный код выхода (exit code).
  - Закрытие через **Cmd+Q** выполняется оператором **только после появления прямого приглашения от регистратора**.
  - Флаг `--desktop-pid` используется исключительно для предварительной проверки внешнего состояния процесса (preflight check), когда регистратор не может перехватить код выхода напрямую.

---

## 3. Проверка готовности стенда (Preflight)

Перед стартом 8-часового прогона выполните валидацию окружения и доступности устройств:

```bash
python3 scripts/desktop_usb_pilot_preflight.py \
  --app "${APP_PATH}" \
  --workspace "${WORKSPACE_PATH}" \
  --desktop-pid "${DESKTOP_PID}" \
  --device "${SERIAL_1}" \
  --device "${SERIAL_2}" \
  --json
```

---

## 4. Управляемый запуск 8-часового пилота

Запуск выполняется строго с контролем кода выхода, новыми целевыми файлами БД и журнала, а также параметрами длительного soak-тестирования:

```bash
python3 scripts/record_desktop_pilot.py \
  --long \
  --desktop-command "${APP_PATH}" \
  --db "${PILOT_DB}" \
  --output "${PILOT_EVENTS}" \
  --device "${SERIAL_1}" \
  --device "${SERIAL_2}" \
  --confirm "${SERIAL_1}" \
  --confirm "${SERIAL_2}" \
  --track-device "${TRACK_SERIAL}" \
  --runs 100 \
  --duration-hours 8 \
  --sample-interval 60 \
  --desktop-shutdown-timeout 60
```

> [!NOTE]
> Приглашение на завершение появится по истечении 8 часов или выполнения лимитов. Нажмите **Cmd+Q** в окне DroidHub Desktop в течение 60 секунд (`--desktop-shutdown-timeout 60`), чтобы подтвердить штатный код выхода.

## 5. Шаблон ритма оператора: 20 циклов USB

На протяжении 8 часов выполняется ровно 20 циклов физического отключения и подключения **одного заранее выбранного телефона** (`${TRACK_SERIAL}`).

### Безопасный регламент цикла
1. **Отключение**: Аккуратно отсоедините USB-кабель телефона `${TRACK_SERIAL}`.
2. **Безопасная пауза**: Выдержите паузу **30–45 секунд**, не подключая кабель повторно, чтобы операционная система и демон DroidHub зафиксировали событие отключения.
3. **Возврат**: Подключите кабель обратно в тот же USB-порт.
4. **Ожидание наблюдения**: Дождитесь подтверждения в выводе регистратора/интерфейсе о появлении стабильного наблюдения устройства (discovery / online), прежде чем переходить к следующему этапу.

## 6. Фиксация результатов при вынужденном прерывании

Если 8-часовой тест вынужденно прерывается оператором или внешними факторами:
1. Завершите процесс DroidHub Desktop штатно через Cmd+Q (не используйте SIGKILL).
2. Зафиксируйте сохранённые промежуточные данные в отдельный журнал без перезаписи основного потока:

```bash
# Сохранение среза накопленных событий при прерывании
cp "${PILOT_EVENTS}" "${INTERRUPT_EVENTS}"
```

3. Зафиксируйте текущее состояние базы данных через снимок для дальнейшего расследования причин остановки.

---

## 7. Анализ результатов, создание снимка и сверка

После штатного завершения пилота оператор выполняет трёхэтапный анализ:

### Шаг 1: Формирование отчёта по soak-тесту
```bash
python3 scripts/desktop_pilot_soak_report.py "${PILOT_EVENTS}" --warmup-sec 600 --strict
```

### Шаг 2: Создание снимка базы данных журнала
```bash
python3 scripts/snapshot_desktop_journal.py \
  --source "${PILOT_DB}" \
  --output "${SNAPSHOT_DB}"
```

### Шаг 3: Аудит и сверка журнала с событиями
```bash
python3 scripts/audit_desktop_pilot_journal.py \
  --events "${PILOT_EVENTS}" \
  --snapshot "${SNAPSHOT_DB}" \
  --json
```

> [!IMPORTANT]
> **Разделение валидации**:
> - Скрипт аудита `audit_desktop_pilot_journal.py` выполняет **проверку целостности журнала** и совпадение агрегатов (отсутствие расхождений между потоком событий и записью в SQLite).
> - **Полный итог пилота** формируется исключительно совокупностью отчёта `desktop_pilot_soak_report.py` и заполненного операторского чек-листа критериев приёмки.

## 8. Критерии приёмки и объяснение порогов

Прогон считается успешным только при соблюдении всех пороговых критериев:

1. **Длительность 8 часов (`8ч`)**:
   - Гарантирует обнаружение медленных деградаций таймеров, дескрипторов файлов и системных шин USB.
2. **Не менее 100 завершённых прогонов (`>=100 завершённых`)**:
   - Подтверждает достаточную статистическую базу выполнения тестовых нагрузок на устройствах без накопления скрытых зависаний.
3. **Не менее 20 циклов переподключения (`>=20 циклов`)**:
   - Подтверждает отказоустойчивость механизма обнаружения устройства и очистки ресурсов при многократных подключениях одного и того же аппарата.
4. **Рост RSS $\le$ 20% после прогрева (`warmup-sec 600`)**:
   - Первые 10 минут (600 секунд) отводятся на прогрев (инициализация библиотек, кэшей и пулов). После прогрева дрейф Resident Set Size (RSS) процесса Desktop не должен превышать 20%, что подтверждает отсутствие утечек памяти.
5. **0 сбоев, потерь и процессов**:
   - **0 сбоев (failures/crashes)**: Отсутствие необработанных исключений и аварийных завершений приложения или adb-сервера.
   - **0 потерь (losses)**: Отсутствие потерянных пакетов/событий жизненного цикла USB.
   - **0 процессов (orphaned processes)**: Полное отсутствие зависших, зомби- или осиротевших дочерних процессов после завершения тестовой сессии.

## 9. Правила безопасности

- Запрещены любые деструктивные команды (`kill -9`, неконтролируемое удаление данных, очистка системных каталогов).
- Запрещена публикация или отправка данных во внешние репозитории (`git push`, внешние вебхуки и публикации). Все собранные логи остаются исключительно в локальном каталоге запуска.
